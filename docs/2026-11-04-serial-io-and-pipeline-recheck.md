# 2026-11-04 串口程序隔離與資料中斷後驗證

## 修正行為

串口讀取不再與 ROS 發布共用執行流程。RX 與 TX 各有三個程序：
硬體 I/O、控制 topic 的 ROS 收發、原始文字／診斷發布。I/O 程序沒有 ROS publisher，
診斷發布等待不會阻止讀取，控制程序停止接收新命令時，TX I/O 仍會自行送零。

程序間使用固定容量的最新值 mailbox，採非阻塞鎖；不累積無上限佇列。
完整組保留 RX 收到時的來源時間與序號，過期快照不重新蓋時間戳、不當作新停車證據。
I/O 自身若超過 0.65 秒未讀取，或串口積壓超過容量，會丟棄無法確認年齡的緩衝資料，
重新累積新鮮四輪組與停車證據。STM32 沒有採樣時間戳，所以這不是 MCU 端延遲量測。

維持 115200、既有封包、小數位數、0.25 秒命令時效、0.35 秒健康時效、
0.65 秒完整組新鮮度、0.8 秒里程計 watchdog、三組跨一秒停車確認及重連退避。
Jazzy 的命令 MessageInfo 字典會正確讀取 source_timestamp；舊速度不會在恢復後重播。

`/chassis/serial_rx_health` 改用與本機四輪組一致的 BEST_EFFORT、depth 1；
TX 訂閱及錄製 QoS 同步調整。診斷失聯不會偽裝成新鮮來源；收不到新資料仍會停車。
明確指定 reliable 訂閱此健康 topic 的外部工具，需要改為 best_effort。
對網頁／雲端 API 沒有 migration 或新欄位要求。

## 資料管線與定位恢復分開

原本 LOCALIZED 期間的底盤／導航／雷達管線中斷，改進入既有 RECOVERING_LOCAL 狀態的
`recovery_step=pipeline_wait`：先取消導航並停止、保留訂單及既有品質歷史。
不立即清除品質歷史，也不因故障當下正在行駛就排除快速恢復。

停妥後，以新鮮來源、TF、健康 AMCL、原始及平滑地圖分數、足夠雷達扇區，
以及 map->odom 相對故障前可信參考的一致性驗證。map->odom 使用 TF 直接取得，
避免拿不同時刻的行駛中 AMCL／odom 位姿相減而誤判跳動。
六次確認各自需要新的地圖觀測與新的 AMCL 來源時間；舊訊息、重複 header、
舊地圖樣本、單一高分或未停妥均不能放行。

通過後恢復 LOCALIZED，原配送程式接續原目標；不以開機 seed 覆蓋位置。
停妥且資料可用時累計最多 8 秒驗證時間；管線仍不完整時暫停該驗證預算，
但整次等待最多 30 秒，不隨斷續資料重新起算。資料持續缺失要求先修復資料管線；
資料已恢復但位置仍不可信，才接回原本位置恢復流程。
真實搬車、全域定位、第二次旋轉／橫移、旋轉安檢與定位品質門檻保持原有保護。

對外 state 名稱保持相容；增加 `/localization/state.pipeline_recheck` 診斷。
`manual_intervention_kind=pipeline` 在此等待階段也用於簡短控制台提示，
如「📡 資料中斷，等待停車驗證」「🔎 資料恢復，驗證既有位置」。

## 量測與錄製

新增 `/chassis/serial_io_diagnostics`，由 RX／TX 各發布 role。
包含 I/O 排程最大間隔、read／解析／IPC／write／ROS publish 耗時、
IPC 跳過次數、過期原始診斷丟棄數，以及來源與 relay 時間戳。
原始 `/stm32_data` 是獨立診斷輸出，卡住時可丟棄過期文字並記數；
判斷來源是否停頓應優先看 `/chassis/wheel_sample` 的來源時間與 I/O 診斷，
不要把原始文字到 bag 的間隔當成 USB 採樣時間。

錄製指令不變，舊 topic 全保留，增加上述診斷：

```bash
bash ~/dev_ws/src/smart-carrier-robot/tools/record_full_system.sh
```

## 驗證範圍

功能回歸覆蓋配送、視覺、電源、API 及新增安全案例；既有 ament copyright/flake8/PEP257
未作為本次功能測試。另用隔離 domain 231、LOCALHOST、臨時 PTY 及零速命令進行整合驗證：
診斷程序暫停、控制發布延遲、資料過期、熱插拔、重新停車確認，以及 odom／定位管理器
消費相同完整組。沒有接觸實體串口，沒有向實車發送導航或非零速度。

- 最終整車功能測試：723 passed。
- 診斷程序 SIGSTOP 3 秒，控制發布延遲 2 秒，RX／TX I/O 最大迴圈間隔約 0.052／0.050 秒。
- 假串口兩次開啟、重連後重新確認停妥，56 組回授、422 次新零速命令被接受，沒有非零封包。
- 暖機後 5 秒量測，四個新增子程序合計約 1.40 個單核心 CPU 百分點；
  各程序 RSS 約 58～77 MiB，含重複計入的共享程式庫。這不包含既有 ROS 主程序，
  也不是整車行駛負載／前後版本效能改善的量測。

測試工具：`tools/verify_serial_hotplug.py`。部署後亦須確認實際 console entrypoint 可啟動／停止。
模擬阻塞測試不能取代場地實測；尚需真實弱網＋VM RViz、行駛中短暫中斷、搬車與多訂單測試。
本版不宣稱已量化降低整車 CPU 或根治所有網路阻塞。

地圖、座標、Nav2 組合模式、速度、MPPI、輪速係數、電源模型、核心 1060、
手動相機／Hailo 驅動及停用更新設定均沒有變更。
