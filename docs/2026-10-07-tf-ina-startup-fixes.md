# 2026-10-07：實測後 TF／INA／待機流程修正

本次僅處理三項問題。電池門檻、電壓來源／標示、充電功率模型、導航速度、
定位可信度與停靠精度均維持原設定；不新增前後端 endpoint、DB 欄位或 migration。

## 修正

1. TF 重試就緒檢查改查 `Time()` 的最新共同有效轉換，不要求尚未到達的
   「精確現在時間」。仍要求 scan/odom 接收與來源時間 <=0.30 秒，完整
   map→base_footprint 轉換時間 <=0.30 秒，來源／TF 最多允許超前 0.10 秒。
   缺失、過期、過度超前的資料一律不得放行。連續就緒 1 秒、每次等待
   15 秒、最多重送 2 次、定位恢復等待與取消優先均保留。
2. INA 探測的 INFO／WARNING 改成固定且分離的 rclpy 呼叫位置，避免同一
   call site 切換 severity 引發 ValueError，造成節點退出。保留同週期 I2C
   重開／重試；不完整寄存器讀取視為失敗。完整週期失敗時清除舊平均窗口，
   發布 unknown／sensor_ok=false，恢復後只用新樣本重新確認，不誤報空槽。
3. 配送啟動對帳改成一次性閘門：收到實際工作（含本機恢復的未完成訂單）
   或 matching request_id 的 empty 回覆後即鎖存完成。只有 tasks 提示而
   尚未收到訂單本體仍會等待。之後雲端 ACK 尚未到達、API 離線或下一次
   claim 查詢中的 waiting，均不得再次禁止返回待機點，也不會在已停妥時
   顯示「啟動等待 API」。每次重啟配送程式仍建立新 nonce 並重新確認。
   本機持久保存 ACK 前仍停車；雲端重送、取消與定位安全限制維持不變。
   重啟時若只有舊的待回報結果，不能當成新訂單已對帳，仍需確認初始佇列。

## 驗證與限制

- `tools/verify_revision.sh`：231 項功能回歸通過（不含既有全域 lint／PEP257）。
- 使用不建立 ROS node 的真實 tf2 Buffer 模擬：最新 odom TF 落後現在
  20 ms 時可通過，舊查詢無法通過；過期／缺失 TF 與延遲感測資料仍被拒絕。
- 唯讀重建本次 rosbag 的 TF：原先誤判時段取樣 14 筆，舊查詢 0/14 通過，
  修正後實際配送回呼 14/14 通過。不重播 bag，也不發任何命令。
- 使用真實 RcutilsLogger 與模擬 I2C：0x40→0x41→0x40，斷線後持續發布
  unknown，恢復後重新確認；短讀取與同週期復原不誤報 empty。
- 執行實際配送閒置分支（導航／發布器替身）：啟動未知時不送待機目標；
  啟動已確認後 API waiting／offline 仍可返回；已停妥不重送、不誤提示。
- 實車仍需驗證 TF 暫態後原訂單恢復，以及斷網／結果背景重送時的返站。
  本次不啟動導航、底盤、INA 節點或發送移動命令。
