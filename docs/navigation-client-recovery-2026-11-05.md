# 配送導航等待回退與待機取消上限（2026-11-05）

## 問題與範圍

13:39–13:45 測試中的定位已恢復正常，但配送導航心跳出現 1.238 秒間隔。
獨立 delivery_goal_guard 因超過既有 1 秒保護門檻而取消目標，造成服務失敗與待機反覆重送。
20038ad 移除了 BasicNavigator 內部的 executor 等待，普通配送與待機迴圈仍只處理一次回呼並 sleep，未能消化高頻輸入。
先前短動作／多執行緒測試未覆蓋實際單執行緒配送與租約守護的組合。

本次僅回退 DeliveryNavigator 的 goToPose、isTaskComplete、cancelTask 改寫，直接繼承原生 BasicNavigator。
有限時 Nav2 啟動確認保留。共用訂閱、JSON 解碼、10 Hz 政策節流、診斷降頻、TF 零等待與 journal 去重保留。
不修改定位、導航、里程計、行充判定、地圖、服務座標或 API 契約。
首次測試同次開機缺少可信位置的啟動限制，以及供電重插造成的 INA 暫態，不以此修正掩蓋。

## 待機重試

- 每個待機目標的導航失敗或非預期取消合計最多三次，10／20 秒非阻塞退避，耗盡後停止自動停靠重送。
- 非預期取消次數跨待機目標保留，整個停靠階段最多三次，避免位置略變、最近點切換時重新取得取消額度。
- 訂單、定位或返航功能主動中斷不計入失敗次數。
- 新服務任務仍可優先執行；下一次服務、成功停妥或手動重啟後重新建立停靠額度。
- /delivery/standby_state 保留既有欄位，新增 unexpected_cancellations，退避／耗盡分別顯示 retry_wait／blocked。
  停靠失敗不回報已到達。

## 驗證方式

- 四個套件的功能回歸測試；排除原有 ament 版權、flake8、PEP257 格式檢查。
- tools/verify_delivery_client_ros.py：客戶端使用 SingleThreadedExecutor，獨立模擬伺服器提供 scan 12 Hz、odom 20 Hz、語意 15 Hz、TF 30 Hz 與 action feedback，客戶端另有 50 Hz 計時器。
- 普通配送等待與正式 go_to_standby 各持續 30 秒，同時使用實際 DeliveryGoalGuard 與原 1 秒門檻；檢查心跳最大間隔、回呼數、成功終態及零非預期取消。
- 額外驗證新訂單可中斷停靠，以及刻意停止心跳後守護程序確實取消目標。
- 導航客戶端驗證不發布速度；其他隔離驗證亦限定 localhost／domain 231 與模擬感測／動作，不連接真實馬達。
