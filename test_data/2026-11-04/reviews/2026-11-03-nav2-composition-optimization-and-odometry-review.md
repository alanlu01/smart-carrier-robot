# 2026-11-03 Nav2 架構、效能與里程計評估

本輪僅唯讀分析，未修改、部署、回退、發布運動指令或重啟。
使用今天三份既有錄製及前輪解析結果，另核對車載實際安裝模組。

## 1. 建議恢復組件模式，不整包回退

建議將 Nav2 的預設啟動方式恢復 `use_composition=True`，傳輸先恢復原配置作為基準。
保留串口重連、回授失聯零速、橫移收尾修正、程序日誌與健康觀察等獨立改動。
獨立模式可留為診斷選項，不適合繼續作現階段預設。

不包含定位管理器與 Delivery；ROS2 程序亦包含 launch，不精確等同 recorder 本身。

同次更新亦改了傳輸設定及健康判斷，因此不能精確分離每項改動的成本。

### 獨立模式實際得失

- 已看到的好處：下午 Nav2 六服務持續 active、14 子程序乾淨退出，未重現本輪容器崩潰。
- 可預期但未直接證明的好處：單一 server 崩潰影響可隔離，程序定位與採樣方便。
  本輪未故意使 server 崩潰，不能宣稱故障隔離續行已驗證。
- 明確代價：Nav2 CPU 合計約從 0.86～1.00 核心增加至 1.76～1.77 核心，整車長期近滿載。
  視覺 fps 中位數由中午全段約 12.89 降至下午約 9.005。兩段場景不同，不能將所有下降精確歸因。
- 未達成目標：人流仍因 TF／odom／回授判斷中斷；不能據此宣稱網路、導航可靠性已改善。
- 客觀保留：下午 map→odom 最長間隔約 0.754 秒，沒有中午約 362 秒缺口；但中午有不同 USB／網路故障，
  下午也同時套用了串口修正，不能把改善全算在獨立程序上。
- 椅腳接近時障礙點存在、APPROACH 介入，不能證明 CPU 是唯一碰撞原因；CPU 飽和會增加時序風險，
  幾何、近距離 STOP 與通行區設計仍需各自處理。
- 記錄與服務健康觀察可以保留在組件模式，並非獨立模式專屬。

早前靜態測試偏重啟動與乾淨退出，未涵蓋全感測、視覺、Delivery、錄製與遠端 RViz 的整車負載，
不足以支持當時直接將獨立模式作為預設。回復組件後仍須保留舊容器故障的追蹤，不能宣稱回退解決所有問題。

官方 Jazzy bringup 亦預設 composed，說明其適合需要最佳化的嵌入式系統：
https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_bringup/README.md

## 2. 保持既有功能的程式最佳化方向

| 優先 | 已見問題 | 預計方向 | 限制 |
|---|---|---|---|
| P1 | 多程序 Nav2 合計成本高 | 恢復組件／原傳輸基準，量測整車 | 不回退串口等安全修正 |
| P1 | Delivery 業務 poll 約每秒百次，同輪反覆 TF 查詢 | 業務決策節流約 10Hz，同輪重用一致快照 | 感測接收、取消、制動及運動安全檢查保留獨立快速路徑 |
| P1 | 多節點各自以收到四行字串的時間組四輪 | 由串口來源產生有時間戳、序號的完整四輪樣本，統一消費 | 保留四輪完整性、過期與停妥證明，不用單純刪 watchdog |
| P2 | 重複 TF、射線幾何及 JSON 診斷 | 快取固定光束角與不可變幾何；每個新樣本更新，摘要／事件發布 | 不重複使用過期淨空判斷，保留關鍵數據量化 |
| P2 | 定位 tick 有約 2.03 秒最大 wall time | 依階段細分計時，隔離／非阻塞處理慢 DDS 或操作 | wall time 不等於 CPU 時間，尚未確認唯一阻塞行 |
| P2 | 完整 costmap、voxel 可視化增加發布／錄製量 | 採更新訊息與完整初始快照，檢查 voxel 顯示是否實際需要 | 更新 recorder 與分析工具確保可重建；不得默默刪原錄製項目 |
| P3 | 已啟動但目前任務程式與 BT 未引用的 route/docking/waypoint 等 | 確認 runtime API 依賴後改成按需啟動 | 不刪除既有使用中的 BT／導航能力；需靜態及完整入口檢查 |

不建議先削減 MPPI、costmap 更新或感測頻率，因為本次近障礙問題需要保持即時性。
也不能承諾上述每項固定釋放多少 CPU；應逐項量測後保留可重現的收益。

## 3. 里程計：單位與動態回授都有待處理

已核對車載 import 的模組：
`/home/robot/dev_ws/build/smart_delivery_core/smart_delivery_core/mecanum_odom_real.py`，
實際解析到 repo source；SHA256 `51bc45a4840d505daa6ed2de4aba3110dc626517fe6e01bf0fee1b7361c82390`。

- 程式 wheel_radius=0.08、rt_to_rad_s=0.000389、yaw_ratio=1.0。
- 實車使用者確認直徑 0.08m，所以半徑應為 0.04m。URDF 輪子半徑亦寫 0.08m，顯示單位需整理。
- 有效線速度尺度為兩者乘積：0.08×0.000389=0.00003112。反推係數可能吸收了原先半徑錯誤；
  不能直接把半徑改 0.04 並宣稱修復。
- 若只是整理單位、維持目前輸出，0.04×0.000778 可保持相同有效尺度；
  這不是新校正，也未證明 0.000778 就是真正 RT→rad/s 定義。須核對 STM32 編碼器、減速比與輸出單位。
- angular_scale 只有註解，沒有生效；yaw_ratio 有參與角速度公式。
- 使用者確認問題是「實車轉超過預期」。若是角度尺度低估，yaw_ratio 應往上修；
  但亦可能由回授低頻、延遲、滑移、停車尾轉造成，不能僅由 Spin 顯示 360° 推算倍率。
- 真實完整輪速約 2Hz；20Hz odom 是持有最近速度再積分，不代表 20Hz 新量測。
  輪速年齡未超 0.8 秒時，仍可能是數百毫秒前的速度，會影響轉向收尾。
- Odometry 的 pose/twist covariance 未填，維持零；不是已量測到零誤差。
  但 AMCL 是讀 TF 的里程變化與 alpha 運動噪聲，不是直接拿這些零 covariance 來當 100% 信任。

### 建議校正流程

先恢復負載與回授穩定，再在實際落地／相同載重下：

1. 外部量測 1～2m 直行、反向及橫移，各做數次，分開評估偏差。
2. 外部實際量測順／逆時針各 360°，至少每方向三次，含低速與正常轉速。
3. 同時記錄真實角度、odom unwrapped 角度、命令停止到輪速歸零的時間。
4. 依 `new_yaw_ratio=old_yaw_ratio×實際角度/odom角度` 校正尺度；
   若結果強烈依速度而變，先處理延遲／煞停，不把所有誤差塞進同一比例。
5. 可參數化幾何與尺度；不需重新掃地圖才能校正。

Nav2 Spin 在 Jazzy 以 local_frame（此車為 odom）累加轉角，實車角度仍須外部量測：
https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_behaviors/plugins/spin.cpp

## 4. 有條件更多依靠里程計，而非雷達一出問題就全域定位

現在 local_costmap 已在 odom，AMCL 提供 map→odom；Nav2 本來就在利用里程計。
頻繁停止還包含自訂 localization_manager／optional runtime 的閘門，不能只改 AMCL 權重就解決。

建議分開處理：

| 情況 | 建議行為 |
|---|---|
| 雷達新鮮、障礙保護正常、輪速與 odom 新鮮；僅地圖吻合短暫下降，最後可信位姿穩定 | 保留任務與既有局部路徑，限速短距離以 odom 推進，等待定位觀測恢復 |
| TF 尚在等待，但實際來源新鮮 | 改善時間對齊／短暫等待，不直接視為位置丟失；不能把舊 TF 任意改成新時間 |
| 掃描、四輪回授或碰撞保護失效；看到近障礙；位姿突變／被搬車；候選射線矛盾 | 停車並驗證，必要時全域定位，不以 odom 掩蓋 |

有限推進候選初值可先評估「最多 1 秒／0.2m／0.2m/s」，任一上限先到就結束；
屬待實測設計，不是已部署門檻。只適用上一刻確實可信、避障仍完整的短暫定位品質下降。
不能在椅腳保護尚未完成、位置已未知或雷達失效時使用。
期間不接受新全域路徑、不完成到站或租還確認；新定位恢復需與 odom 預測位置一致，
否則停車驗證。實作需由一致 TF 權責管理，不能另開第二個 map→odom 發布者互相覆蓋。

### AMCL 的里程計信任

當前 alpha1～alpha5 全為 0.8，表示運動噪聲估得較大；它們不是雷達／里程計的百分比分配。
校正後可由實測分別降低，特別區分直行、橫移、旋轉；不能直接全部設成很小。
OmniMotionModel 中旋轉噪聲與平移、橫移噪聲皆受 alpha 影響，
校正與調參需配合，不以縮小 covariance 或改名為高可信代替。
